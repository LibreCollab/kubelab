The CNI plugin gives Pods IPs and routes traffic between nodes.

- Every Pod gets its own IP.
- The CNI handles cross-node routing and often NetworkPolicy.
- Overlay and routed modes trade complexity for performance.

```bash
kubectl get pods -o wide
kubectl describe pod api
```

**Failure modes.** CNI failures break Pod-to-Pod and Pod-to-Service traffic while the API and scheduling still look healthy. Missing routes, wrong MTU, an unready CNI DaemonSet, or a node that cannot reach the Pod network all produce connection failures.

**Verify.** Verify Pod IPs, node routes, CNI Pods, and a direct Pod-to-Pod request. Check Service endpoints separately from network connectivity. A working CNI means every node can route to Pod IPs and DNS works from a Pod on each node.

**Evidence to capture.** Compare Pod IPs and node routes from both ends of a connection; a single-node test can miss a broken cross-node path.

Repeat the check after any node or CNI change; stale routes are a common source of intermittent failures.
